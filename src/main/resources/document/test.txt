# Java 文本切片工具库设计说明

## 一、项目背景

RAG 系统在构建知识库时，通常需要先从 PDF、Markdown、图片或普通文本中提取内容，然后再将长文本切割成适合向量化的片段。文本切割质量会直接影响召回效果、上下文完整性和最终回答质量。

本工具库希望提供统一的文本提取接口和文本切割接口，使 SpringBoot 项目可以用一致的方式处理不同来源的文档。

## 二、核心功能

文本提取层负责把原始文档转换为统一的 DocumentContent。PDF 文档优先使用 PDFBox 提取文本层；如果文本层为空、乱码较多或长度不足，则可以使用 OCR 识别扫描页；对于复杂版式、图片说明、表格内容，也可以交给 AI 模型做增强解析。

文本切割层负责把 DocumentContent 中的正文切成多个 TextChunk。切割策略包括固定字符切割、自然段切分、标题切分、自定义符号切分、语义切分和 AI 切分。

## 三、固定字符切割测试段落

这是一个较长的段落，用于测试固定字符切割是否会在指定长度附近寻找更自然的断点，而不是直接从一句话中间截断。比如当最大长度设置为一百二十个字符时，切割器应该优先选择句号、问号、感叹号、分号、逗号或空格附近作为边界，从而尽量保留语义完整性。如果实在找不到合适边界，才允许按字符长度强制切断。

## 四、自然段切分测试

第一段：自然段切分应该识别空行作为段落边界。这个段落主要描述文本切片的背景和目标。

第二段：这里是另一个自然段。它应该被切成独立片段，或者在长度较短时与相邻段落合并，具体取决于 minChunkSize 和 maxChunkSize 的配置。

第三段：如果这个段落很短，也要测试短文本合并逻辑。

## 五、自定义符号切分测试

下面的文本使用自定义符号进行分隔::第一部分介绍 PDF 提取::第二部分介绍 OCR 识别::第三部分介绍 AI 解析::第四部分介绍文本切片。

需要特别注意，网址不能被错误切开：https://example.com/docs/api/v1/text-splitter?lang=zh_CN&mode=test，也不能切坏邮箱地址 support@example.com，版本号 v1.2.3 和文件路径 /data/rag/docs/readme.md 也应该被保护。

## 六、语义切分测试

文本切片工具的第一类用户是 Java 后端开发者，他们关注的是接口是否清晰、依赖是否轻量、是否容易集成到 SpringBoot 项目中。因此，工具库应该提供简单的默认配置，并允许用户按需扩展策略。

另一类用户是 RAG 应用开发者，他们更关注切片结果是否适合向量检索。对他们来说，切片不应该只按字符长度处理，而应该尽量保留问题、定义、步骤和结论之间的上下文关系。

这两个段落虽然都在讨论用户，但关注点不同。语义切分器应该识别主题变化，并尽量把不同主题切成不同片段。

## 七、AI 切分测试

请根据下面内容判断合理的切分边界。第一部分讲文本提取，第二部分讲文本切片，第三部分讲异常处理，第四部分讲未来扩展。AI 切分时应该优先保持每个主题完整，而不是机械地按固定长度切开。

文本提取：系统需要支持 PDFBox、OCR 和 AI 模型解析。PDFBox 适合有文本层的 PDF，OCR 适合扫描件和图片，AI 模型解析适合复杂版式和多模态内容。

文本切片：系统需要支持固定字符切割、自然段切分、标题切分、自定义符号切分、语义切分和 AI 切分。不同策略应该共享统一的返回结构。

异常处理：当输入为空、文件不存在、OCR 失败或 AI 调用失败时，工具库应该抛出明确异常，调用方可以自行决定是否重试、降级或记录日志。

未来扩展：后续可以支持 Word、HTML、Excel、PPT 等更多文档格式，也可以加入向量模型辅助语义边界判断。

## 八、表格和列表测试

| 策略 | 适用场景 | 风险 |
| --- | --- | --- |
| 固定字符切割 | 超长文本兜底 | 容易切断语义 |
| 自然段切分 | 结构清晰文本 | 段落过长 |
| 标题切分 | Markdown 或文档章节 | 标题识别不准 |
| 自定义符号切分 | 日志、问答、规则文本 | 可能切坏网址 |
| 语义切分 | RAG 知识库 | 实现复杂 |
| AI 切分 | 高质量切片 | 成本较高 |
